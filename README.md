# scaffold

CRUD generation for an ASP.NET Core MVC project built on custom EditorTemplates.

The default scaffolder emits presentation directly into views — raw `<input>`
tags with hardcoded classes. When the project already owns presentation through
`Views/Shared/EditorTemplates`, that output is worse than nothing. This tool
emits **annotated ViewModels plus explicit `EditorFor` calls** and lets the
templates do the rendering.

## Folder layout

This is a standalone solution. It is **not** added to the project it scaffolds.

```
ScaffoldTool/
├── Scaffold.sln
├── README.md
├── .gitignore
└── Scaffold/
    ├── Scaffold.csproj
    ├── Program.cs            CLI: inspect, generate, doctor, eject-*
    ├── EmbeddedFiles.cs      reads baked-in templates and rules
    ├── ProbeRunner.cs        materialises and runs the probe
    ├── TemplateCatalog.cs    globs Views/Shared/EditorTemplates
    ├── HintRules.cs          applies rules to raw probe facts
    ├── IrBuilder.cs          raw facts + rules + templates -> model.json
    ├── IrMerge.cs            preserves hand edits across re-inspection
    ├── Planner.cs            IR -> flat render data
    ├── Renderer.cs           Scriban wrapper
    ├── Generator.cs          maps templates to output paths
    ├── rules.json
    ├── Probe/
    │   ├── ProbeProgram.txt  the EF IModel reader (embedded, not compiled)
    │   └── ProbeProject.txt  the probe csproj template
    └── Templates/
        ├── Controller.scriban
        ├── ViewForm.scriban
        ├── ViewIndex.scriban
        ├── ViewDetails.scriban
        ├── ViewDelete.scriban
        ├── ViewModelForm.scriban
        ├── ViewModelListItem.scriban
        ├── ViewModelDetails.scriban
        ├── ViewModelSearch.scriban
        └── ViewModelIndex.scriban
```

Files under `Probe/` and `Templates/` are **embedded resources, not compiled**.
`ProbeProgram.txt` deliberately has no `.cs` extension: it references EF types
this project does not have, and a `.cs.txt` name would trip the SDK's resource
naming convention (see below). All thirteen are checked by a build target — a
missing one fails `dotnet build` rather than surfacing as a runtime error.

## Install

From nuget.org:

```powershell
dotnet tool install --global StarterAspMVCEditorTemplates.ScaffoldTool
scaffold doctor
```

From source, for development:

```powershell
cd C:\src\ScaffoldTool
dotnet build
dotnet pack .\Scaffold\Scaffold.csproj -c Release
dotnet tool install --global --add-source .\Scaffold\nupkg StarterAspMVCEditorTemplates.ScaffoldTool
scaffold doctor
```

Both install the same `scaffold` command. The package id carries the
`StarterAspMVCEditorTemplates` prefix on purpose: the generated views render
through those editor templates, and the tool produces near-useless output in a
project that does not have them.

Then, from any project directory:

```powershell
cd C:\src\Zeiterfassung\src\Zeiterfassung
scaffold inspect
scaffold generate --dry-run
scaffold generate --force
```

## Tests

```powershell
dotnet test                                       # everything
dotnet test --filter Category!=Integration        # fast only, no build of the fixture
dotnet test --filter FullyQualifiedName~Template  # one area
```

Four layers, cheapest first:

- **Unit** — `TemplateSelectionTests`, `RequirednessTests`. Table-driven over
  `RawModel`, a fluent builder for synthetic probe output. No EF, no database,
  no build: a regression reproduces from three lines rather than a schema.
- **IR** — `IrBuilderTests`, `IrMergeTests`. Declaration order, search operator
  selection, cascade warnings, list columns, and that hand edits survive a
  re-inspect while schema facts are re-derived.
- **Compile** — `GeneratedCodeCompilesTests`. Parses generated C# with Roslyn.
  This layer is what would have caught `{ get; set; };` (CS1597) and nullable
  annotations in an `<auto-generated` file (CS8632) before they reached a real
  project. `TemplateIntegrityTests` also asserts every template parses as
  Scriban and that no view template nests a quoted literal inside a quoted
  tag-helper attribute.
- **Golden** — `GoldenTests`. Rendered output committed under
  `Scaffold.Tests/Golden/`, so a template change is a reviewable diff. A missing
  file is written and passes (git is the review gate); only a mismatch fails,
  and it writes `<name>.actual` alongside for diffing. Accept an intended change
  with `$env:SCAFFOLD_UPDATE_GOLDEN = "1"; dotnet test`, then read the diff: if
  it is not obviously an improvement, it is a regression.
- **Integration** — `ProbeIntegrationTests`. Runs the real probe against
  `Scaffold.TestModel`. Slow, because it builds a project.

### Scaffold.TestModel

A fixture EF project, not a sample app. It exists because no single real project
has every shape at once. It carries: `= null!` versus `= string.Empty`
initializers, a `required` navigation, a small enum and a large one, `[UIHint]`
overriding a name convention, a nullable FK, many-to-many via skip navigation,
an owned type, a `Guid` key, a composite key, a concurrency token, and both
`Cascade` and `Restrict` delete behaviours.

**When adding a generator feature, add the entity property that triggers it here
first.** That is what stops the tool being tuned to one project's schema.

## Publishing

Published to nuget.org as
[`StarterAspMVCEditorTemplates.ScaffoldTool`](https://www.nuget.org/packages/StarterAspMVCEditorTemplates.ScaffoldTool/)
using **Trusted Publishing** — no API key is stored anywhere. The workflow
exchanges a short-lived GitHub OIDC token for a temporary NuGet key valid for
about an hour.

This is no longer optional in practice: NuGet API keys created from
17 August 2026 expire after 30 days, and keys created before that date stop
working on 1 November 2026.

### One-time setup on nuget.org

Sign in, click your username, choose **Trusted Publishing**, and add a policy:

| Field | Value |
|---|---|
| Repository Owner | `Buttersdontfly` |
| Repository | `ScaffoldTool` |
| Workflow File | `publish.yml` |
| Environment | *(leave empty)* |

The workflow file is the **file name only**, not the `.github/workflows/` path.
The policy is bound to it, so renaming `publish.yml`, the repository, or the
owner breaks publishing until the policy is updated to match.

On a **private** repository the policy starts as temporarily active for 7 days.
NuGet needs the GitHub repository and owner IDs to pin the policy, and it only
learns them from a successful publish. Publish once inside that window and it
becomes permanent; otherwise restart the window.

### One-time setup on GitHub

Add a repository secret `NUGET_USER` holding your **nuget.org username** — the
profile name, not the email address. It is not a credential; it is in a secret
only to keep it out of the workflow file.

### Releasing

```powershell
# bump <Version> in Scaffold/Scaffold.csproj, commit, then:
git tag v0.6.0
git push origin v0.6.0
```

The tag is the source of truth for the published version: the workflow passes
`-p:Version=` from it, so the tag and the package can never disagree. The
`<Version>` in the csproj matters only for local `dotnet pack`.

`workflow_dispatch` accepts a version manually for a re-run.

### Why two workflows

`ci.yml` runs on every push and pull request, including a verification `pack` —
a packaging error then surfaces on the commit that caused it rather than at tag
time, when a failed publish has already burnt a version number.

`publish.yml` exists separately because the trusted publishing policy is bound
to a filename. Its `NuGet/login` step sits immediately before the push, since
the temporary key expires in about an hour.

### Adding an approval gate

To require manual approval, create a GitHub environment named `release`, add
`environment: release` to the `publish` job, and set **Environment** to
`release` in the nuget.org policy. All three have to match.

## Rebuilding the tool

`dotnet tool install` resolves by **version**, and NuGet caches resolved packages
in `%USERPROFILE%\.nuget\packages\starteraspmvceditortemplates.scaffoldtool\<version>`. Re-packing the same
version number therefore reinstalls the *cached* package and your changes appear
to do nothing.

Always bump `<Version>` in `Scaffold.csproj` before packing:

```powershell
cd C:\src\ScaffoldTool
# edit <Version> in Scaffold\Scaffold.csproj, e.g. 0.1.0 -> 0.1.1
dotnet pack .\Scaffold\Scaffold.csproj -c Release
dotnet tool update --global --add-source .\Scaffold\nupkg StarterAspMVCEditorTemplates.ScaffoldTool
scaffold doctor
```

If the version is genuinely unchanged and you just want a clean slate:

```powershell
dotnet tool uninstall --global StarterAspMVCEditorTemplates.ScaffoldTool
Remove-Item -Recurse -Force $env:USERPROFILE\.nuget\packages\starteraspmvceditortemplates.scaffoldtool
dotnet tool install --global --add-source .\Scaffold\nupkg StarterAspMVCEditorTemplates.ScaffoldTool
```

### `scaffold doctor`

Reports the path of the running binary, its build timestamp, and every embedded
resource. Three required names must appear:

```
Scaffold.Probe.ProbeProgram.txt
Scaffold.Probe.ProbeProject.txt
Scaffold.rules.json
```

If any are missing, the `.txt` and `.json` files were not embedded.

### Why the probe sources are not named `Program.cs.txt`

The SDK property `EmbeddedResourceUseDependentUponConvention` is on by default.
It peels the final extension off each embedded resource and, if what remains
looks like a source file, binds the resource as `DependentUpon` that file and
derives the manifest name from **its** namespace and type — silently overriding
`LogicalName`.

`Program.cs.txt` minus `.txt` is `Program.cs`, which matches the tool's own
`Program.cs`, so the resource shipped under an unpredictable name and lookups
failed. `Probe.csproj.txt` minus `.txt` is `Probe.csproj`, not a source file, so
it was unaffected — which is exactly why one worked and the other did not.

The files are therefore named `ProbeProgram.txt` and `ProbeProject.txt`, with no
`.cs` segment, and the convention is switched off in `Scaffold.csproj` as well.

```
target project ──► probe (separate process) ──► raw-model.json
                                                     │
                          rules.json ────────────────┤
              EditorTemplates/*.cshtml ──────────────┤
                                                     ▼
                                model.json  ◄──── merge with existing
                                     │
                                     ▼
                        Scriban templates ──► controllers, ViewModels, views
```

## Commands

```bash
scaffold doctor
scaffold inspect --project ./Zeiterfassung.csproj
scaffold inspect --project ./Zeiterfassung.csproj --report --verbose

scaffold generate --dry-run                 # list files, change nothing
scaffold generate --entity Activity --force
scaffold generate --force                   # every entity

scaffold eject-rules                        # rules.json
scaffold eject-templates                    # .scaffold/templates/*.scriban
```

## Output per entity

Eleven files, all overwritten on `--force`:

```
ViewModels/{Entity}CreateModel.cs      ViewModels/{Entity}SearchModel.cs
ViewModels/{Entity}EditModel.cs        ViewModels/{Entity}IndexModel.cs
ViewModels/{Entity}ListItemModel.cs    Controllers/{Route}Controller.cs
ViewModels/{Entity}DetailsModel.cs
Views/{Route}/Index.cshtml   Create.cshtml   Edit.cshtml   Details.cshtml   Delete.cshtml
```

Every ViewModel is `partial`, so hand-written additions live in a separate file
(`{Entity}EditModel.Custom.cs`) and survive regeneration. `IValidatableObject`
for cross-field rules — "end must be after start" — belongs there; the generator
cannot infer it.

## Editing templates

`scaffold eject-templates` copies the Scriban templates into
`.scaffold/templates/`. An ejected file always wins over the built-in one, so
changing house style means editing a template rather than rebuilding the tool.

Scriban is used because its `{{ }}` delimiters do not collide with Razor's `@`,
which is what makes T4 and Razor-generating-Razor painful when the output is
itself a `.cshtml`.

One rule when editing a view template: never write a quoted string literal
inside a quoted tag-helper attribute. `asp-all-route-data="SortRoute("title")"`
does not parse. Declare a local in the `@{ }` block and pass that instead.

## Why a separate probe process

Reading EF Core's `IModel` means loading the target's assemblies. Doing that
in-process would require the tool's EF version to match the project's, which is
where most scaffolders become fragile.

Instead the tool writes `obj/scaffold-probe/` containing a tiny project that
`ProjectReference`s the target, then runs it. The probe compiles against **your**
EF version, so drift is structurally impossible. The folder is rewritten on every
run and carries its own `.gitignore`.

### DbContext resolution order

1. `IDesignTimeDbContextFactory<T>` — the same hook `dotnet ef` uses. Found by
   reflection, so the probe needs no compile-time reference to
   `Microsoft.EntityFrameworkCore.Design`.
2. A detected provider configured with a dummy connection string. Building
   `IModel` never opens a connection; the provider is needed only so its
   conventions and type mappings load. Override with `--provider` and
   `--connection`.

Recognised providers: SqlServer, Npgsql, Sqlite. Anything else needs a
design-time factory.

## Partial success is the design goal

Nothing hard-fails on an unrecognised shape:

| Situation | Result |
|---|---|
| Rule wants a template that isn't in `EditorTemplates/` | falls back to the type template, adds a `TODO(scaffold)` |
| Owned type with no `typeMap` entry | flattened to scalar columns, `TODO(scaffold)` |
| Getter-only collection navigation | Details-only, absent from Create/Edit |
| Entity with no `DbSet` or no key | skipped, reason printed |
| Identity tables | skipped by namespace and base-type check |

## What the IR owns versus what the probe owns

Re-running `inspect` after a migration merges rather than overwrites. The probe
is authoritative about schema; you are authoritative about intent.

Preserved across re-inspection: `display`, `additionalViewData`, `search`,
`items`, `include`, `order`, `sortable`, `typeMap`, `editor.templateOverride`,
`validation.requiredOverride`, and the entity-level `route`, `controller`,
`displayColumn`, `index`.

Re-derived every time: `clrType`, `nullable`, `maxLength`, `kind`, `principal`,
`navigationRequired`, `deleteBehavior`, and `validation.required`. A stale
requiredness answer would silently emit wrong validation attributes, so it is
never preserved — use `requiredOverride` if you disagree with it.

A rename reads as a drop plus an add. `--report` lists both so a rename never
quietly loses hand-written labels.

## Conventions the tool relies on

- **Async action names.** `IndexAsync` routes as `Index` because
  `SuppressAsyncSuffixInActionNames` defaults to `true`. That makes
  `nameof(IndexAsync)` the wrong string, so a per-controller `Actions` const
  class is generated instead.
- **Items are per-call.** `Dropdown`, `RadioGroup` and `CheckboxList` read
  `ViewData["items"]`, supplied through `additionalViewData` on a single
  `EditorFor`. `EditorForModel()` cannot give different options to different
  properties, so views are generated as explicit per-property `EditorFor` lines.
- **Requiredness reads initializers.** `= null!` means the value must be set;
  `= string.Empty` means empty is expected and `[Required]` would be wrong. EF
  marks both non-nullable, so the initializer breaks the tie.
- **Search operators map onto existing templates.** `contains` → `String`,
  `range` → a `From`/`To` pair of nullable scalars, `equals` → `Dropdown`,
  `choice` → a `string?` on `RadioGroup`. No new editor templates are required.

## Known gaps

- Many-to-many is not searchable and not a grid column: filtering a linked set
  needs an `Any()` predicate and a different control.
- Collection navigations are Details-only. Inline add/remove rows need index
  juggling that is not worth blocking the rest of the output.
- Owned types must be mapped explicitly in `typeMap`; no suffix convention is
  inferred.
